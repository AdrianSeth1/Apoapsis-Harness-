# ADR 0066: A literal response shape in the frontier planning handoff

Date: 2026-07-26

Status: Accepted

Extends ADR 0032 (discovery and frontier planning handoff) and ADR 0019
(Architect Mode planning foundation).

## Context

A frontier planning response for session `DISC-7D87B2379D8E` was rejected with
eight `extra_forbidden` errors, all in two objects:

```text
plan.delivery_contract.artifacts                    Extra inputs are not permitted
plan.delivery_contract.definition_of_done           Extra inputs are not permitted
plan.delivery_contract.deployment_requirements      Extra inputs are not permitted
plan.delivery_contract.operational_requirements     Extra inputs are not permitted
plan.verification_strategy.levels                   Extra inputs are not permitted
plan.verification_strategy.acceptance_validation    Extra inputs are not permitted
plan.verification_strategy.nonfunctional_validation Extra inputs are not permitted
plan.verification_strategy.exit_criteria            Extra inputs are not permitted
```

The plan was otherwise good: ten components, eight integration contracts, five
architecture decisions, a five-item pre-mortem, seventeen slices. Every one of
those sections used the correct field names. Only two objects were wrong, and
the whole plan was discarded because of them.

The handoff was not withholding the schema. `build_frontier_planning_markdown`
embeds `FrontierPlanningResponseEnvelope.model_json_schema()` in full — about
26 KB with 19 `$defs`. But that schema is written for a validator, not a
reader. To learn what `delivery_contract` accepts, a model must follow
`plan` → `anyOf[$ref: ArchitecturePlan]` → `properties.delivery_contract` →
`$ref: PlanDeliveryContract` → `$defs.PlanDeliveryContract.properties`.

The correlation is exact and is the whole diagnosis. Grepping the Markdown
builder for the three nested section names returns **zero** prose mentions:
`delivery_contract`, `runtime_design`, and `verification_strategy` appear
nowhere except inside the raw schema blob. Every section the model got right
is one the Markdown also describes in prose. Two of the three sections that
existed only behind `$ref` came back invented. (`runtime_design` happened to
match, which is luck, not evidence the indirection worked.)

The invented names are not careless — `artifacts`, `definition_of_done`,
`deployment_requirements`, `exit_criteria` are all reasonable names for those
concepts. That is precisely the failure mode: given a plausible concept and no
literal key list in view, a model writes the plausible key.

This is expensive to get wrong. The failure surfaces only after the model has
written an entire architecture plan, and the operator has to take the whole
thing back to their subscription session to correct it.

## Decision

`build_frontier_planning_markdown` now emits, **before** the JSON Schema, a
fully expanded literal example of the response object under the heading
"The exact shape to copy": every permitted key at every nesting level, with
placeholder values and no indirection. The schema follows it, still complete
and still labelled authoritative.

The example is generated by `apoapsis.specification.skeleton.json_skeleton`,
which walks a Pydantic model's fields and recurses into nested models, lists of
models, literals, and enums. It is **derived from the models themselves**, so
it cannot drift away from what validation enforces. A hand-written example
would have rotted the first time a field was added.

The accompanying prose states plainly that these are all the keys that exist,
that every object rejects unknown keys, and that the nested objects are the
ones easy to guess wrongly — naming them.

Ordering matters: the literal shape comes first so a reader who stops after
the first code block already has everything they need.

Cost is small. The expanded skeleton is about 5 KB against the schema's 26 KB.

### What is deliberately not changed

- **The schema stays strict.** `extra="forbid"` is what stops a planner
  smuggling in a `status` or `approved` field (ADR 0019). Relaxing it to
  accept unknown keys would silently discard content the model believed it
  was delivering, which is worse than rejecting it.
- **The schema is still embedded.** It remains the authoritative statement.
  The skeleton is an aid to reading it, not a replacement.
- **The manual frontier repair handoff is untouched.**
  `ManualFrontierResponseEnvelope` is flat, with no nested models and so no
  `$ref` indirection to misread.

## Consequences

- A frontier model can copy the response shape rather than reconstruct it from
  `$ref` traversal, at the point in the document where it decides what to
  write.
- The handoff grows by roughly 5 KB, well inside the transport and domain
  ceilings raised in ADR 0065.
- `json_skeleton` is generic and available for any other strict envelope the
  harness asks an external model to produce.
- This reduces a known failure mode; it does not eliminate it. A model can
  still ignore a literal example. If invented keys recur, the next step is a
  bounded schema-repair round that reports the permitted keys back for
  correction without re-running planning — a separate decision.

## Alternatives rejected

- **Inline all `$defs` into one flat schema.** Removes indirection but makes
  the schema block substantially larger and more repetitive, and still asks
  the reader to parse JSON Schema rather than see the answer.
- **Loosen `delivery_contract` / `verification_strategy` to accept extra
  keys.** Trades a loud, correct rejection for silent data loss, and erodes
  the `extra="forbid"` guarantee that protects the authority boundary.
- **Accept the invented keys by renaming the model fields.** The frontier
  model's guesses are not more correct than the harness's own vocabulary, and
  the next model would guess differently.
- **Do nothing and treat it as model non-compliance.** The information was
  technically present, but the section the model got wrong is exactly the
  section the document never stated in readable form. That is a documentation
  defect, not just a model error.
