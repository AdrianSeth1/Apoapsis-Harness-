# ADR 0063: Changed-path classification and structured-edit EOF normalization

Date: 2026-07-26

Status: Accepted

Supersedes: none. Extends ADR 0046 (no-progress guard), ADR 0057 (create_file
and malformed-diff no-progress guard), and ADR 0017 (worktree fingerprint).

## Context

The 2026-07-26 live Laguna run against `C:\Users\aryam\apoapsis-live-test`
(task `TASK-EF33C00E5BD4`) reached the end-to-end path for the first time.
Worktree isolation and the authority boundary held, and Apoapsis correctly
refused to report success when the model implemented `subtract()` but never
landed the requested test. That refusal is the design working and is not
changed here.

Two harness-side defects were found in the same run, and they blocked any
useful reliability measurement because they mix harness mechanics into what
would otherwise be a measurement of model capability:

1. Reviewer-facing `files_changed` was
   `["__pycache__/calc.cpython-314.pyc", "calc.py",
   "tests/__pycache__/test_calc.cpython-314.pyc"]`. Two of those three entries
   were written by Apoapsis's own verification run. A reviewer reading that
   list cannot tell what the model did, and the scratch repository had no
   `.gitignore` rules that would have hidden them.

2. The agent burned 13 patch attempts and 20 turns while reaching verification
   exactly once. Attempts 3 through 13 for `tests/test_calc.py` were the same
   patch, SHA-256
   `7F233AFDBE1EA65FB94EBE391A75FCF1E0CECEFA32EEF61568A38C4683605B06`, rejected
   every time by `git apply --check`:

   ```text
   new blank line at EOF
   error: 1 line adds whitespace errors
   ```

The second point is the important one and is not simply "Laguna is bad at
diffs." The failing edit arrived through the structured `replace_text` action.
The model supplied `path`, `old_text`, and `new_text`; **Apoapsis** synthesized
the unified diff from them. A structured request that deterministically becomes
a rejected patch can never succeed on retry, because the same input produces
the byte-identical output. Meanwhile the existing no-progress guard for this
failure class only matched `propose_patch`, so it never fired, and the
guidance the model received said "Your last propose_patch was rejected" for an
action the model had not taken.

## Decision

Make the task report and the controller answer three separate questions, and
keep them separate.

### 1. What source/test files did the model actually change?

A new deterministic classifier, `apoapsis.repository.changed_paths`, splits a
changed-path listing into `reviewable`, `generated_byproducts`, and `rejected`.
Classification is purely name-based over a normalized relative path
(`__pycache__/**`, `*.py[cod]`, `.pytest_cache/**`, coverage and build caches,
`node_modules/**`, and similar), makes no filesystem or Git call beyond the
tracked-file listing it is given, and preserves the existing path-safety
policy: `.git/**`, `.apoapsis/**`, `.sol/**`, absolute/drive paths, and `..`
escapes are rejected outright, exactly as before.

`RepositoryInspector` grows `classified_changed_paths()`,
`reviewable_changed_paths()`, and `generated_byproduct_changed_paths()`.
`AgentSessionResult.changed_files` and `LocalPowerReviewPackage.changed_files`
now carry only the reviewable surface, and both gain a separate
`generated_byproducts` field.

**A tracked path is always reviewable, even when its name matches a generated
pattern.** Somebody deliberately committed it, so a legitimate modification to
it is the model's work. Hiding it would be the mirror image of the defect this
ADR fixes.

**The classifier deliberately does not consult `.gitignore`.** Reviewer output
must be correct against repositories Apoapsis did not initialize, and existing
projects cannot be assumed to carry the ignore rules `apoapsis init` writes.
`apoapsis init` does now add Python cache ignores, but that is ergonomics for
new projects only and nothing depends on it.

### 2. Did verification mutate the worktree with generated byproducts?

`VerificationRunner` sets `PYTHONDONTWRITEBYTECODE=1` in
`HARNESS_VERIFICATION_ENVIRONMENT`, applied beneath the allowlisted host
environment, so a Python verification command no longer writes `__pycache__`
into the tree it is measuring. An explicitly configured command can still
override it through the existing per-command `environment` mechanism and no
other path.

This is prevention, not concealment. Byproducts produced some other way are
still classified rather than erased: `RepositoryInspector.changed_paths()`
remains the raw audit view and continues to show everything, and the audit
artifact `normalized_patch_failure.worktree_changed_paths` is unchanged.

### 3. Is the model making a new attempt, or resending the same rejected patch?

Three changes, all in `apoapsis.agent`:

- `RepositoryInspector.replacement_patch()` normalizes end-of-file blank
  content that the edit *introduced*, so a `new_text` ending in an extra blank
  line can no longer synthesize a patch Git's whitespace policy must reject.
  A file whose EOF shape was already unusual before the edit is preserved
  untouched, because normalizing it would silently widen the model's requested
  change beyond what the audit trail records. An edit that reduces to *only*
  added EOF blank content is refused explicitly rather than applied as a no-op.
  `new_file_patch()` canonicalizes its content the same way.

- The no-progress guard `_repeated_no_progress_stop_reason()` now recognizes
  the `git apply` whitespace failure class for every edit action
  (`propose_patch`, `replace_text`, `create_file`), not just `propose_patch`.
  Three same-class failures in a row stop the session instead of consuming the
  remaining patch and turn budgets.

- The next-action requirement for this class is now action-neutral. It states
  that the *generated patch* was rejected by Git's whitespace policy, that
  resending the same edit produces the identical patch and will fail
  identically, and what specifically to change.

### Completion policy is unchanged

The live sample's correct outcome remains `human_review_required`. The
requested test was never landed and the configured unittest command only ran
the pre-existing `test_add`. Nothing here treats "verification passed" as
evidence that a requested test exists. If acceptance proof needs to change,
that is a separate ADR.

## Consequences

- Reviewers see a change surface that answers one question and answers it
  correctly, on repositories Apoapsis did not initialize.
- Audit evidence still records that verification mutated the worktree; the two
  facts are reported in different fields rather than merged or dropped.
- A structured edit that deterministically becomes a rejected patch is either
  normalized so it applies, refused immediately, or stopped after three
  attempts. It can no longer consume a whole budget.
- The reliability-measurement gate in `NEXT_STEPS.md` can be lifted only after
  a live Laguna rerun of the same subtract task confirms this behavior; the
  deterministic tests are necessary but not sufficient evidence.
- Models remain untrusted typed proposers. Nothing here weakens path safety,
  patch policy, or `propose_patch` parsing.

## Verification performed

```powershell
python -m unittest tests.test_agent_loop tests.test_verification `
    tests.test_local_power_session tests.test_cli   # 88/88, 1 expected skip
python -m unittest discover -s tests -v             # 916 tests, 12 skips,

python -m compileall -q src tests                   # passed
git -c core.whitespace=blank-at-eol,space-before-tab,cr-at-eol diff --check
```

Plain `git diff --check` remains noisy in this checkout because of the known
mixed CRLF/LF working-tree state; the line-ending-aware form above passed.

The 11 full-suite failures are pre-existing and unrelated to this ADR. Each was
reproduced in a scratch copy of the tree with `_normalized_eof` reduced to the
identity function and `HARNESS_VERIFICATION_ENVIRONMENT` emptied, which is the
only honest way to attribute them. They are inventoried in `HANDOFF.md` under
"Known limitations and active risks". Two `tests/test_cli.py` expectations were
updated deliberately, because `apoapsis init` now writes Python cache ignores;
that module passes 10/10.

No live Laguna run was performed. This is fake-provider evidence only.

## Alternatives rejected

- **Rely on `.gitignore`.** Correct only for repositories the harness
  initialized. The live failure happened in one that was not.
- **Drop generated paths from all output.** Destroys the evidence that the
  harness's own verification run mutated the worktree.
- **Relax `git apply`'s whitespace strictness.** Weakens patch policy to
  accommodate one sample, and would let genuinely malformed hand-authored
  diffs through.
- **Normalize whitespace anywhere in `new_text`.** Would silently rewrite
  meaningful content the model asked for. Only whitespace-only lines (existing
  behavior) and introduced EOF blank content (this ADR) are canonicalized.
