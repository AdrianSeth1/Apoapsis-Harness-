## Required design outcome

The fix should make the task report and controller answer three separate
questions cleanly:

1. What source/test files did the model actually change?
2. Did verification mutate the worktree with generated byproducts?
3. Is the model making a new attempt, or repeatedly sending a request that
   deterministically becomes the same rejected patch?

Keep these separate. Do not hide generated clutter by pretending it never
existed in audit evidence, and do not let generated clutter corrupt the
reviewer-facing change surface.

## Implementation plan

1. Add a deterministic changed-path classifier.

   It should distinguish at least:

   - tracked source/test/config changes;
   - untracked model-authored files that are reviewable;
   - untracked generated byproducts such as `__pycache__/**`, `*.py[cod]`,
     `.pytest_cache/**`, coverage caches, and common build/cache directories.

   Use it where human-facing reports and escalation/review packages list
   changed files. Preserve strict path-safety checks and never include
   `.git/**`, `.apoapsis/**`, secrets, or out-of-root paths.

2. Prevent Python verification from creating bytecode when Apoapsis controls
   the verification environment.

   Set `PYTHONDONTWRITEBYTECODE=1` in `VerificationRunner`'s base environment
   unless an explicitly configured verification command overrides it. The Local
   Power sandbox already does this for model-requested shell commands; ordinary
   configured verification should do the same.

3. Do not rely on `.gitignore` alone.

   Updating `apoapsis init` to add Python cache ignores for new projects is good
   ergonomics, but reviewer output must be correct even when the target
   repository has no useful ignore rules. Existing projects cannot be assumed to
   have been initialized with the new template.

4. Fix structured edit normalization for EOF blank-line failures.

   `RepositoryInspector.replacement_patch()` already canonicalizes whitespace-
   only lines in `new_text`. Extend the structured edit path so it cannot
   synthesize a patch that adds forbidden blank-only lines at EOF. This should
   be deterministic and audited through the existing patch artifacts. Do not
   relax raw `propose_patch` parsing or patch policy.

5. Generalize the repeated whitespace-rejection no-progress guard.

   The guard in `BoundedAgentSession._repeated_no_progress_stop_reason()` should
   apply to repeated `replace_text` as well as repeated `propose_patch` when the
   root error is the same `git apply` whitespace class. If the model sends the
   same structured edit and Apoapsis synthesizes the same rejected patch three
   times, stop early instead of consuming the remaining patch and turn budgets.

6. Improve the next-action requirement after a structured whitespace rejection.

   The current guidance says "Your last propose_patch was rejected..." even
   when the failing action was `replace_text`. Make the message action-neutral:
   explain that the generated patch was rejected by Git whitespace policy, that
   resending the same edit will fail identically, and that the next edit must
   remove the trailing blank/whitespace content or use a narrower replacement.

7. Keep completion strict.

   The sample's correct outcome is still `human_review_required`: the requested
   test was not landed, and the configured unittest command only ran the
   pre-existing `test_add`. Do not add any policy that treats "verification
   passed" as sufficient evidence that a requested test exists. If acceptance
   proof changes are needed, make them a separate ADR; do not fold them into
   this patch-loop fix.

## Required deterministic coverage

Add fake-provider tests before any new live Laguna run:

- A local agent run where verification writes `__pycache__/*.pyc` but
  `report.files_changed` and the human-review package list only source/test
  changes.
- A `replace_text` edit whose `new_text` contains an extra blank-only EOF line
  and previously produced the `new blank line at EOF` rejection; prove the
  structured edit now applies or is normalized deterministically.
- A repeated `replace_text` whitespace-rejection sequence that stops after
  three same-class failures instead of spending the full patch budget.
- A regression proving tracked generated-looking files, if already tracked in
  the repository and legitimately modified, are not silently hidden from
  reviewer output merely because their names match an ignore pattern.
- Verification runner environment coverage proving `PYTHONDONTWRITEBYTECODE=1`
  is present by default and that an explicit command environment can override
  it only through the existing configured-command mechanism.

## Verification checklist

Run focused tests first:

```powershell
python -m unittest tests.test_agent_loop tests.test_local_power_session tests.test_cli -v
```

Then run the required project checks:

```powershell
python -m unittest discover -s tests -v
python -m compileall -q src tests
git diff --check
```

If plain `git diff --check` is noisy only because of the known mixed CRLF/LF
state, also run and report the line-ending-aware check:

```powershell
git -c core.whitespace=blank-at-eol,space-before-tab,cr-at-eol diff --check
```

Do not refresh the handoff Snapshot with unobserved results.
